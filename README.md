### Задание 1 СУБД
Кейс
Крупная строительная компания, которая также занимается проектированием и девелопментом, решила создать правильную архитектуру для работы с данными. Ниже представлены задачи, которые необходимо решить для каждой предметной области.

Какие типы СУБД, на ваш взгляд, лучше всего подойдут для решения этих задач и почему?

1.1. Бюджетирование проектов с дальнейшим формированием финансовых аналитических отчётов и прогнозирования рисков. СУБД должна гарантировать целостность и чёткую структуру данных.

1.1.* Хеширование стало занимать длительное время, какое API можно использовать для ускорения работы?

1.2. Под каждый девелоперский проект создаётся отдельный лендинг, и все данные по лидам стекаются в CRM к маркетологам и менеджерам по продажам. Какой тип СУБД лучше использовать для лендингов и для CRM? СУБД должны быть гибкими и быстрыми.

1.2.* Можно ли эту задачу закрыть одной СУБД? И если да, то какой именно СУБД и какой реализацией?

1.3. Отдел контроля качества решил создать базу по корпоративным нормам и правилам, обучающему материалу и так далее, сформированную согласно структуре компании. СУБД должна иметь простую и понятную структуру.

1.3.* Можно ли под эту задачу использовать уже существующую СУБД из задач выше и если да, то как лучше это реализовать?

1.4. Департамент логистики нуждается в решении задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов. СУБД должна уметь быстро работать со связями.

1.4.* Можно ли к этой СУБД подключить отдел закупок или для них лучше сформировать свою СУБД в связке с СУБД логистов?

1.5.* Можно ли все перечисленные выше задачи решить, используя одну СУБД? Если да, то какую именно?

Приведите ответ в свободной форме.

Ответ.
1.1 Для задач бюджетирования проектов, формирования финансовых аналитических отчетов и прогнозирования рисков, наилучшим выбором будут реляционные SQL базы данных. Они обеспечат целостность данных и четкую структуру, что критически важно для финансовых данных. В частности, базы данных, такие как PostgreSQL или MySQL, могут быть хорошим выбором, поскольку они обеспечивают ACID-совместимость, поддерживают сложные SQL-запросы и предоставляют возможности для аналитики и отчетности.
1.1* Для ускорения работы хеширования можно использовать специализированные библиотеки, алгоритмы, методы параллелизации или, в некоторых случаях, графические процессоры (GPU). Выбор подхода зависит от задачи и характеристик данных. Библиотеки: OpenSSL, Intel IPP (Integrated Performance Primitives), Google's CityHas. Алгоритмы: xxHash, MurmurHash, древовидные методы хэширования.

1.2 Для девелоперских проектов с отдельными лендингами, а также для CRM системы, которая обрабатывает данные по лидам, хорошим выбором будут NoSQL базы данных, такие как MongoDB или Apache Cassandra. Для лендингов: NoSQL базы данных часто используются для работы с большими объемами неструктурированных данных, что может быть полезно при сборе и хранении данных с различных лендингов. MongoDB, например, обеспечивает гибкую модель данных, горизонтальное масштабирование и хорошую производительность при обработке больших объемов данных. Для CRM: NoSQL базы данных также могут быть полезны для CRM системы, поскольку они могут обеспечить быструю запись и чтение данных, а также гибкую модель данных, которая позволяет быстро адаптироваться к изменениям в структуре данных. Apache Cassandra, например, известна своей способностью обеспечивать высокую производительность и отказоустойчивость при работе с большими объемами данных.  
1.2* Да, возможно закрыть эту задачу одной СУБД, можно использовать NoSQL базу данных, такую как Apache Cassandra.

1.3 База данных PostgreSQL может быть хорошим вариантом, т.к. имеет простую и понятную структуру, обеспечивает ACID-совместимость, мощные средства для определения структуры данных (таблицы, отношения), а также поддерживает сложные SQL-запросы, что может быть полезно при формировании отчетов и анализе данных. 
1.3*  Да, можно использовать ту же СУБД, что и для финансовых данных (например, PostgreSQL или MySQL), если они обеспечивают нужную структуру для хранения и извлечения данных. Для этой задачи можно использовать таблицы и индексы, чтобы быстро находить нужные материалы.

1.4  Для решения задач по быстрому формированию маршрутов доставки материалов по объектам и распределению курьеров по маршрутам с доставкой документов можно будет использовать графовыю базы данных. Графовые базы данных специально разработаны для работы с данными, имеющими сложные связи, что делает их эффективным инструментом для решения задач, связанных с маршрутизацией и распределением ресурсов. 

1.4* Для подключения отдела закупок к СУБД логистов можно рассмотреть PostgreSQL с расширением PostGIS. Эта СУБД позволяет эффективно работать с географическими данными (маршруты, карты), а также быстро обрабатывать связи между объектами (например, курьеры и объекты доставки).

1.5* Для всех перечисленных выше задач можно использовать одну СУБД, например: PostgreSQL с расширениями, т.к это универсальная реляционная СУБД, которая поддерживает как традиционные реляционные операции, так и расширения для работы с геоданными (PostGIS), временем (TimescaleDB), а также имеет возможность работы с неструктурированными данными через JSON.

6. Закрытие транзакции.

### Задание 4 Кластеры

Необходимо производить большое количество вычислений при работе с огромным количеством данных, под эту задачу выделено 1000 машин.

На основе какого критерия будете выбирать тип СУБД и какая модель распределённых вычислений здесь справится лучше всего и почему?

Приведите ответ в свободной форме.


При выборе СУБД для работы с большим количеством данных и вычислений необходимо учитывать следующие критерии:
 - Тип данных и их структура (структурированные или неструктурированные)
 - Объем данных и скорость их обработки
 - Требования к согласованности данных
 - Масштабируемость системы
 - Производительность при параллельных вычислениях

Оптимальным выбором будет модель распределенных вычислений MapReduce по ряду причин:

- Принцип работы MapReduce идеально подходит для параллельной обработки
- Эффективное распределение нагрузки между узлами
- Автоматическое управление отказоустойчивостью
- Оптимизация использования ресурсов кластера

Выбор СУБД должен основываться на:
- Для структурированных данных - SQL СУБД (PostgreSQL, MySQL)
- Для неструктурированных данных - NoSQL СУБД (MongoDB, Cassandra)
- Для обработки больших данных - Hadoop с поддержкой MapReduce
